# 文档规范

> 面向：维护仓库文档的贡献者。

## 信息架构

| 目录 | 内容 |
| --- | --- |
| `01-overview/` | 产品定位、范围和系统全景 |
| `02-architecture/` | 当前架构、模块职责和稳定边界 |
| `03-guides/` | 使用、配置、开发、测试和维护流程 |
| `04-roadmap/` | 当前工作方向与状态说明 |
| `05-history/` | 已退役路线和精炼后的演进背景 |

一个事实只保留一个权威位置。入口页只做阅读导航；项目内部的 API 和实现细节优先放在源码旁 README；仓库级文档只解释跨项目关系、稳定合同和使用路径。

## 命名与语言

- 目录和普通 Markdown 文件名使用小写 `kebab-case` 英文，例如 `installation-and-configuration.md`。目录入口的 `README.md`、根目录 `CHANGELOG.md` 以及已有语言入口 `README_CN.md` 是约定俗成的例外。
- 正文以中文为主；项目名、类型名、命令、路径、API 和无法准确翻译的技术术语保留英文并使用反引号。
- 标题使用简洁中文，不混用无意义的 title case、全英文标题或日期后缀。
- 使用相对 Markdown 链接；不写入本机绝对路径、临时目录或构建输出链接。

## 结构与表达

长期文档优先采用“定位/范围 -> 设计或流程 -> 边界 -> 相关入口”的结构。需要生命周期说明时，可在标题后使用简短引文标明适用范围；不为每篇稳定文档增加会迅速过期的日期、通过数或进度百分比。

表格用于稳定的职责、配置或映射对照；代码块只保留可复制的最小示例。避免在入口页堆积命令输出、任务流水账、实现文件逐行复述或没有来源的“全部完成”表述。

## 当前、计划与历史

- 当前架构事实必须能由源码、测试或可复现命令支持。
- 路线图只保留当前状态和已接受的下一阶段优先级。计划必须有明确目标、依赖、owner 和验收标准；完成后将稳定结论收敛到当前状态、架构或指南，不保留过程清单。
- 历史探索、退役路线、旧审计和旧测试快照只保留在 `05-history/` 的精炼说明中。详细旧材料由 Git 历史承担追溯责任。
- 版本演进统一记录在仓库根目录 `CHANGELOG.md`，不在产品或架构文档中重复。

## 更新检查

提交前确认：目录和文件名符合命名规则；链接指向现有权威文档；新内容没有复述历史材料；涉及公共行为的改动已同步到相应架构或使用指南；`git diff --check` 无格式错误。
