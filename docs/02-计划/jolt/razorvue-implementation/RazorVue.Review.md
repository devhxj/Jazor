# RazorVue 评审

> 状态：历史评审产物。
> 定位：初始 RazorVue 文档集的已归档评审快照。

## 1. 评审范围

本次评审检查：

1. 设计是否内部连贯
2. 实现路径是否正确分阶段
3. HMR 和 sourcemap 是否被足够早地预留
4. 仓库是否有一个现实的首次交付切片

## 2. 第一轮：开发者评审

### 2.1 当前已连贯的部分

设计在以下方面在技术上是连贯的：

- 入口通过 `[ECMAScriptModule]` 保持统一
- lowering 在静态模块和 RazorVue 组件之间干净地拆分
- 基础层级固定为 `ComponentBase -> JazorComponent -> VueComponent`
- 第一阶段通道不依赖于手动 `.razor` 解析
- 分析器加生成代码分析用于语义发现，而非宿主传输
- `DenoHost` 仍然是最终构建所有者

### 2.2 在本轮之前仍然薄弱的部分

在最后一轮之前，HMR 主要以分散的预留语言存在。

这使得以下三个方面不够显式：

- 稳定的身份所有权
- 保守的变更分类
- 后续运行时更新的精确编译器/宿主划分

新的 HMR 文档集弥补了这个差距。

### 2.3 仍然存在的技术风险

仍值得跟踪的主要技术风险：

1. 生成的 Razor 代码形状可能比第一阶段提取当前假设的变化更大
2. 从当前 `ModuleCatalog` 到并行 `RazorVueCatalog` 的过渡仍需要代码证明
3. `using` 驱动的组件解析将需要谨慎的歧义诊断
4. Vue 库描述符将需要严格的扩展边界，以避免重新引入通用框架抽象

### 2.4 开发者结论

从开发者角度来看，架构在该评审点上已足够清晰，可以开始首个实现里程碑（PR1）。

下一步工作不应重新打开设计。
它应该开始证明分析器拆分和基础类型骨架。

## 3. 第二轮：项目负责人评审

### 3.1 交付形态

交付计划已适当分阶段。

当前文档集避免了一种常见的失败模式：

- 试图在一个里程碑中证明完整的 RazorVue、HMR、sourcemap、生态集成和宿主运行时

相反，工作被分解为：

- 第一阶段的核心主路径里程碑
- 为后续里程碑预留的 HMR 和 sourcemap 元数据
- 显式的首次 PR 系列

### 3.2 范围控制

范围现在已得到控制，因为文档明确拒绝了：

- 通用多框架 UI 抽象
- 完整的 Blazor 运行时兼容性
- 早期的 `.vue` SFC 输出
- 第一阶段运行时 HMR 实现
- 第一阶段完整 sourcemap 输出

这对于交付可信度很重要。

### 3.3 组织清晰度

责任线现在足够显式，可支持未来的并行工作：

- 编译器团队拥有发现、提取、lowering、产物身份和清单生产
- 宿主团队拥有最终编译、打包和后续的 HMR 运行时行为
- 库集成可以扩展描述符和 HMR 提示，但不能重新定义基础契约

### 3.4 项目负责人结论

从项目负责人角度来看，计划现在已可投资。

它具备：

- 清晰的首个里程碑边界
- 显式的非目标
- 有界的风险
- 从文档到首个实现里程碑的可见路径

## 4. 最终评审结论

经过评审的 RazorVue 文档集定义了一条从架构设计到首个实现里程碑的可行路径。

正确的下一步是：

1. 落地 `JazorComponent` 和 `VueComponent`
2. 在静态模块和 RazorVue 入口之间拆分分析器模式
3. 添加首批 RazorVue 诊断和测试

## 5. 一句话结论

在那个评审点上，RazorVue 已被充分文档化，可以停止在设计中打转，开始证明首个实现里程碑。
