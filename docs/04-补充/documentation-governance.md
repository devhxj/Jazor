# 文档治理规则

## 目标

文档应帮助读者快速回答三个问题：当前系统如何工作、某项工作处于什么状态、下一步应查阅哪份资料。入口文档、专题设计、实施计划和历史审计必须保持清晰分层。

## 目录职责

| 目录 | 职责 |
| --- | --- |
| `docs/01-目标/` | 产品定位、长期设计和技术边界 |
| `docs/02-计划/` | 当前实施计划、里程碑、WBS 和验收标准 |
| `docs/03-完成/` | 状态快照、评审结果和验证证据 |
| `docs/04-补充/` | 治理规则和不改变主契约的补充说明 |
| `docs/05-遗弃/` | 不再指导当前实现的历史材料 |

源码旁的 README、API 说明和映射文档优先描述当前代码契约；仓库级文档负责说明模块关系、产品边界和阅读路径。

## 状态标签

新文档应使用明确的状态语义，例如：

- `活跃参考`：当前设计或公共契约入口；
- `活跃计划`：正在执行的实施计划；
- `当前状态快照`：对当前实现和验证结果的记录；
- `历史资料`：仅保留背景或审计价值；
- `生成产物`：由工具生成，不应手工维护。

## 编辑规则

1. 长期设计放入 `01-目标`，并在文档中心建立入口。
2. 当前实施方案放入 `02-计划`，必须包含目标、依赖和验收标准。
3. 完成或评审记录放入 `03-完成`，必须包含日期、范围、命令和结果。
4. 计划或状态失效后，更新状态并移入 `05-遗弃`，或在原位置明确标注为历史资料。
5. 细分文档不重复定义公共契约；发生冲突时，以源码、测试和当前目标文档为准。
6. 不在入口文档中堆积命令输出、阶段流水账或未经验证的完成度数字。

## 证据规则

文档中的当前结论必须能够由源码、测试或可复现的构建命令验证。历史审计报告中的路径、测试数量和问题清单只代表记录时点，引用时必须注明其时间范围。

以下目录默认不纳入仓库文档体系：`.tmp/`、NuGet 缓存、`node_modules/` 和工作树生成目录。
