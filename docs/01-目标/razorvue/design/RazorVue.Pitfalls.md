# RazorVue 陷阱

本文档记录 RazorVue 最可能的实现错误。

其目的是阻止未来工作漂移回感觉熟悉但对已选择的设计结构上错误的路径。

相关文档：

## 1. 重新扩展为通用 UI 抽象

这是最大的战略陷阱。

错误方向：

- 将 Razor 视为中性 UI DSL
- 过早尝试统一 React/Vue/Svelte
- 引入框架不可知的 UI 核心作为一流目标

失败原因：

- Vue 语义过早扁平化
- 范围在第一个循环关闭之前爆炸
- 创作体验在概念上分裂

正确方向：

- 保持第一阶段 Vue 优先
- 仅在 Vue 路径证明稳定后提取共享思想

## 2. 假设 `[ECMAScriptModule]` 意味着一条降低路径

另一个常见陷阱是将共享入口标记视为共享降低。

错误方向：

- 检测 `[ECMAScriptModule]`
- 将所有内容发送到一条编译器路径

失败原因：

- 普通静态模块和 Razor 组件不具有相同的输入形状
- 生成的 Razor 组件结构根本上由构建器驱动

正确方向：

- 统一入口
- 立即拆分降低

## 3. 对抗 `ComponentBase`

试图完全避免 `ComponentBase` 在纸面上看起来更清晰，但这不是这里的实用路径。

错误方向：

- 使 `JazorComponent` 独立于 `ComponentBase`
- 试图将 Razor 组件与其实际技术基质分离

失败原因：

- Razor 工具围绕 `ComponentBase` 构建
- C# 没有多重继承
- 产生的创作体验变得不稳定

正确方向：

- 接受 `ComponentBase` 作为技术基础
- 使用 `JazorComponent` 和 `VueComponent` 在其上重新定义语义

## 4. 将 `JazorComponent` 变成第二个框架核心

反向陷阱也很危险。

错误方向：

- 不断向 `JazorComponent` 添加行为
- 让它成长为调度/状态/运行时主机

失败原因：

- 职责立即模糊
- `VueComponent` 失去意义
- 编译器和运行时概念折衷为一个模糊的基础类

正确方向：

- 保持 `JazorComponent` 瘦
- 将 Vue 优先创作 API 放在 `VueComponent` 上

## 5. 使 `VueComponent` API "对来说足够通用"

这是一个伪装为面向未来的抽象陷阱。

错误方向：

- 现在使 `Ref/Reactive/Emit/Provide` 通用和框架不可知

失败原因：

- 它们不再是真正的 Vue 语义
- 实现复杂性增长
- 第一阶段不再是关于可用的 Vue 优先循环

正确方向：

- 让 `VueComponent` API 显式为 Vue 形状

## 6. 在源生成器排序上构建主管道

这是最可能的实现错误之一。

错误方向：

- 假设 Razor SG 首先运行
- 假设另一个 SG 可以安全消费其输出

失败原因：

- 源生成器排序不是此管道的稳定基础
- 架构变得依赖于时序而非契约驱动

正确方向：

- 分析器加生成代码分析进行语义提取
- 后续构建移交给 `DenoHost`

## 7. 将生成的 Razor 代码视为普通用户方法体

分析器可以看到生成的代码，但这不会使生成的 Razor 方法成为普通输入。

错误方向：

- 将 Razor 生成方法视为普通方法
- 重用静态模块降低路径

失败原因：

- 模板语义已经降低为构建器模式
- 直接重用静态路径失去太多结构

正确方向：

- 首先提取渲染树结构
- 将该渲染树降低为 Vue 语义

## 8. 直接从 `BuildRenderTree` 操作生成 Vue 代码

这看起来很快，但在结构上很脆弱。

错误方向：

- 遍历构建器操作
- 立即发送 Vue 代码

失败原因：

- 难以测试
- 难以调试
- 难以附加源始
- 对生成的 Razor 模式更改脆弱

正确方向：

- 首先构建最小渲染树模型
- 从该模型降低为 Vue

## 9. 按需猜测组件契约

另一个容易的错误：

- 仅在访问调用站点时推断 props/events/slots

失败原因：

- 插槽解析变得不稳定
- 绑定语义漂移
- 生态系统组件难以集成

正确方向：

- 首先提取 `VueComponentDescriptor` 风格契约
- 在降低和调用站点验证期间一致使用它

## 10. 让未知组件属性静默传递

这通常感觉很方便，尤其是在早期。

错误方向：

- 允许未知的组件侧属性传递到运行时

失败原因：

- 拼写错误成为静默错误
- 契约提取失去价值
- 诊断急剧下降

正确方向：

- 对 HTML 在适当的地方保持灵活
- 对组件契约保持严格

## 11. 让继承的 `ComponentBase` 成员重新定义模型

因为 `JazorComponent` 继承 `ComponentBase`，某些成员可见。

错误方向：

- 静默支持 `StateHasChanged`
- 静默支持 `ShouldRender`
- 静默支持 `SetParametersAsync`

失败原因：

- Vue 优先语义被拉回 Blazor 调度
- 创作者期望在两个运行时模型之间分裂

正确方向：

- 诊断这些用法
- 将它们保持在主 RazorVue 模型之外

## 12. 完全延迟 HMR 和 sourcemap 思考

这是最昂贵的未来陷阱之一。

错误方向：

- 忽略 HMR 和 sourcemap 直到阶段二
- 仅发送最终 JS 文本加一个通用内容哈希
- 不保留始链

失败原因：

- 后续 sourcemap 变成重建而非构建时组合
- HMR 退化为粗重新加载行为
- 工件结构必须重新设计

正确方向：

- 现在不完全实现 HMR/sourcemap
- 但现在保留源始元数据并分离工件标识

## 13. 让 HMR 或 sourcemap 驱动整个阶段一形状

相反的陷阱也存在。

错误方向：

- 围绕假设的 HMR 或 sourcemap 需求重新设计核心降低

失败原因：

- 主循环甚至尚未闭合
- 在阶段一证明有用之前实现成本激增

正确方向：

- HMR/sourcemap 在阶段一中是元数据优先的关注
- 它们保留结构，而非定义主降低

## 14. 在编译器和 `DenoHost` 之间拆分依赖所有权

这是一个典型的职责边界失败。

错误方向：

- 编译器解析部分依赖拓扑
- `DenoHost` 解析另一部分

失败原因：

- 行为变得难以解释
- 导入/打包规则漂移
- 后续主机功能变得难以稳定

正确方向：

- 编译器声明依赖
- `DenoHost` 解析/构建它们

## 15. 过早深度集成生态系统包

错误方向：

- 通过深度支持 Vuetify/Router/Pinia 开始阶段一

失败原因：

- 生态系统细节开始驱动核心编译器架构
- 主 RazorVue 循环仍未证明

正确方向：

- 首先完成 Vue 优先主管道
- 稍后添加基于描述符/注册表的扩展的生态系统支持

## 16. 在阶段一中过度支持 Razor 语法

另一个频繁的范围陷阱：

- 立即尝试广泛的 Razor 兼容性

失败原因：

- 提取器复杂性在主管道稳定之前上升
- 许多不支持的角落分散了渲染树恢复和 Vue 降低的注意力

正确方向：

- 首先支持小的、显式模板子集

## 17. 仅使用端到端测试

这会减慢调试并隐藏真正的失败位置。

错误方向：

- 仅依赖最终发送的 Vue 模块或主机级测试

失败原因：

- 不可能判断失败是否来自：
  - 发现
  - 契约提取
  - 逻辑提取
  - 渲染树提取
  - 降低
  - 发送

正确方向：

- 在每个编译器阶段保持分层测试

## 18. 在实现时让阶段一范围扩展

最大的交付风险不是技术上的不可能。
它是不受控制的范围增长。

错误方向：

- 在最小循环闭合之前添加更多语法
- 添加更多运行时行为
- 添加 HMR
- 添加 sourcemap
- 添加生态系统包
- 添加 SSR
- 添加 `.vue` 输出

失败原因：

- 每个阶段保持未完成
- 架构在证明自己之前漂移

正确方向：

- 强制最小循环
- 将延迟项显式延迟

## 19. 最后提醒

RazorVue 将主要失败，如果实现不断漂移回：

- 通用抽象
- 依赖于时序的生成器假设
- 静态模块重用
- 模糊的主机/编译器所有权
- 为未来 HMR/sourcemap 的元数据丢失

最安全的路径不是具有最多功能的路径。
它是保留已决定边界的路径。
